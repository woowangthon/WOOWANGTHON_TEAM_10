# 보안 점검 기록 (2026-11-02)

구현을 시작하기 전에 두 가지를 점검했다. ① Claude 클라우드 세션에서 개발하는 방식 ② GitHub 저장소 상태.
각 항목은 **확인한 사실**과 **대응**으로 나눠 적었다.

## 1. 클라우드 세션 점검

| 항목 | 확인한 사실 | 판단 / 대응 |
| --- | --- | --- |
| 실행 위치 | 사용자 PC가 아니라 격리된 일회용 클라우드 컨테이너. 세션이 끝나면 회수됨 | 사용자 PC 파일에는 접근하지 않음. 남길 작업은 반드시 커밋·푸시 |
| GitHub 권한 | 이 세션은 `alwjrqns/mijuk00` 한 저장소에만 접근하도록 범위가 제한됨 | 다른 저장소는 건드릴 수 없음 |
| 작업 브랜치 | Claude는 `claude/...` 작업 브랜치에만 푸시. `main`에는 직접 푸시하지 않음 | 사용자가 PR로 내용을 보고 합칠지 결정 |
| 네트워크 | 외부 통신은 모두 정책이 적용된 프록시를 거침. npm 패키지 저장소에는 접속 가능 | 패키지 설치 시 공급망 위험이 있음 → §3 규칙 적용 |
| 컨테이너 환경변수 | 플랫폼이 넣은 인증 변수가 있음. AWS/GCloud 변수는 길이 14자의 자리표시 값으로, 실제 키 형식(AWS는 20/40자)이 아님. GitHub 토큰은 프록시가 관리 | 이 값들을 출력하거나 파일·커밋에 넣지 않음 |
| 커밋 서명 | 커밋은 서명된 상태로 기록됨(Claude 명의) | 누가 작성했는지 추적 가능 |
| 연결된 외부 서비스 | 세션에 Notion 연결이 붙어 있음 | 이번 작업에는 사용하지 않음. 쓸 일이 생기면 먼저 물어봄 |
| 사용자 업로드 파일 | 아이디어 문서는 세션 업로드 폴더에만 있음 | 저장소에 복사하지 않음. 원본 자료는 `private/`(gitignore)에만 둠 |

**클라우드 세션 자체에 큰 위험은 없다.** 다만 아래 두 가지는 남는 위험이다.
- Claude가 만든 코드에도 실수가 있을 수 있다 → PR 단위로 검토하고, 권한·근거 검증 같은 핵심 로직에는 자동 테스트를 둔다.
- 설치하는 npm 패키지가 오염됐을 가능성 → §3의 규칙을 적용한다.

## 3. 구현할 때 지킬 보안 규칙

1. **API 키는 저장소에 절대 넣지 않는다.** 로컬에서는 `.env.local`(커밋되지 않음), 배포 환경에서는 Vercel의 Environment Variables에 넣는다. 채팅창에도 붙여넣지 않는다.
2. `NEXT_PUBLIC_`으로 시작하는 변수는 브라우저에 그대로 노출된다. Anthropic 키, DB 주소, Supabase service role 키는 이 이름으로 만들지 않는다.
3. LLM 호출과 DB 쓰기는 **서버 코드에서만** 한다. 브라우저 코드에서는 하지 않는다.
4. 패키지는 널리 쓰이는 공식 패키지만 설치하고, `package-lock.json`을 커밋하고, `npm audit`을 확인한다. 이름이 비슷한 가짜 패키지에 주의한다.
5. 권한 검사, 팀 경계, 근거 ID 검증, 철회 반영에는 자동 테스트를 둔다(구체화 문서 §9).
6. 시연·평가 데이터는 가상 메모만 쓴다. 실제 개인정보나 킥오프 전사 원문은 넣지 않는다.
7. 공개 전환 직전에 전체 커밋 기록을 다시 한 번 비밀정보 검사한다.

## 4. 사용자가 직접 해야 하는 설정 (Claude는 권한이 없거나 하면 안 됨)

- [ ] GitHub 계정 **2단계 인증(2FA)** 켜기 — Settings → Password and authentication
- [ ] `main` 브랜치 보호 — 저장소 Settings → Branches(또는 Rules) → `main`에 "PR 필수", "강제 푸시 금지"
- [ ] **Dependabot alerts** 켜기 — 저장소 Settings → Security(Code security) — 비공개 저장소에서도 무료
- [ ] 저장소를 공개로 전환한 뒤 **Secret scanning + Push protection** 켜기
- [ ] Anthropic·Supabase 등에서 키를 만들 때 **사용 한도(월 예산)** 설정, 대회가 끝나면 키 폐기

## 5. 변경 기록과 2단계(AI 연결 지점) 보안 설계 — 2026-11-02 추가

### 계획에서 바뀐 점
- 로그인은 Supabase Auth 대신 **직접 구현**했다(Node 내장 `crypto`의 scrypt 해시와 HMAC 서명 쿠키). 외부 계정·키 없이 시연할 수 있다. 데이터베이스는 어느 PostgreSQL이든 쓸 수 있다.
- 로그인 시도 제한은 서버 메모리 기준이라 서버가 재시작되면 초기화된다. 대회 시연 규모에서 감수하는 한계다.
