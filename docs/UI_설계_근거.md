# 화면과 가입 흐름의 설계 근거

확인일: 2026-11-10. 아래는 실제 제품과 공식 디자인 문서에서 확인한 원칙을 이 서비스에 맞게 해석한 기록이다. 특정 글꼴이나 스타일이 AI 제작 여부를 판별해 준다는 근거는 없다. 목표는 사용자가 지적한 낯선 글꼴과 과도한 강조를 줄이고, 실제 작업에 필요한 구조를 분명히 하는 것이다.

[NN/G의 실제 AI 프로토타이핑 도구 평가](https://www.nngroup.com/articles/ai-prototyping/)는 구체적인 제품 맥락과 시각적 지시가 부족하면 비슷한 일반형 화면이 나오고, 작업의 우선순위와 세부 사용 흐름은 별도 판단이 필요하다고 설명한다. 이에 이 앱의 실제 작업인 메모 읽기·팀 참여·기록 재접속을 기준으로 화면을 정리했다. 특정 서체를 바꾸는 것만으로 제작 방식의 인상이 사라진다고 보지 않는다.

## 화면

### 실제 CSS 변경

- 시스템 한글 글꼴을 우선하고, Windows에서 한글·영문에 서로 다른 서체가 섞이던 기존 우선순위를 정리했다. Windows에는 맑은 고딕 Regular/Bold 파일이 실제 있는 것을 확인했다. 다른 OS의 실제 표시 서체는 해당 기기에서 별도 확인해야 한다.
- 제목의 650 굵기와 음수 자간을 제거했다. 문서 제목은 24px의 보통 굵기를 사용한다. 목록은 선택한 항목에만 굵은 제목을 둔다.
- 11~12px였던 보조 안내를 최소 13px로 올렸다. 읽기 본문과 머리 영역의 최대 너비를 740px로 제한했다.
- 한국어 설명은 어절을 우선해 줄을 바꾸고, 공간보다 긴 단어·주소는 필요한 위치에서 줄을 바꾼다. 좁은 사이드바에서 한 단어가 한 글자씩 다음 줄로 떨어지던 모습을 수정했다.
- 기존 밝은 테마·어두운 테마와 모바일 목록 접기, 메모 선택 도구 모음 동작을 유지한다. 모바일 작은 버튼은 최소 높이 44px로 맞춘다.
- 로그인 코드 등 다시 접속할 때 필요한 내용은 복사 가능한 고정폭 텍스트로 보여 준다. 장식 카드나 배너 문구로 계정 복구의 한계를 가리지 않는다.

위 원칙은 이 서비스에 대한 설계 판단이며, 사용자 선호나 사용성 향상을 검증한 실험 결과는 아니다. 최종 확인에는 실제 앱의 데스크톱·모바일 화면과 두 사용자 흐름을 사용한다.

### 화면 확인

로컬 실제 앱에서 시작 화면과 가상 팀의 메모 화면을 각각 1440px, 390px, 320px 너비로 확인했다. 여섯 경우 모두 가로 넘침과 브라우저 JavaScript 오류가 없었다. 스크린샷을 읽어 사이드바 설명의 어절 중간 줄바꿈이 개선됐는지 별도로 확인했다. Windows Chrome의 너비를 바꾼 확인이므로 실제 iOS·Android 기기 검증을 대신하지 않는다.

### 적용한 흐름과 경계

1. **처음 시작하기**: 팀에서 사용할 이름과 새 팀 이름 또는 초대 코드만 입력한다. 서버가 무작위 160비트 코드와 30분짜리 서명 발급권을 준비한다. 이 단계에는 DB에 계정·팀을 만들지 않는다.
2. **개인 로그인 코드 보관 후 시작**: 코드를 복사·파일로 보관하고 보관 확인을 한 뒤, 개인 UUID 계정·팀 생성 또는 참여·멤버십을 한 트랜잭션으로 처리한다. 초대가 잘못되면 계정도 남기지 않는다. 가입 응답을 잃어도 이미 보관한 코드로 다시 들어갈 수 있다. 서버 DB에는 코드의 SHA-256 해시만 저장한다. 코드·발급권 원문은 주소·감사 로그·브라우저 localStorage에 쓰지 않는다.
3. **다시 들어가기**: 개인 로그인 코드 한 칸으로 같은 계정을 연다. 이름·팀 이름·팀 초대 코드는 로그인 수단이 아니다. 같은 이름의 팀원이 있어도 UUID와 개인 메모는 서로 다르다. 로그인 쿠키는 7일간 유지되며, 코드와 로그인 세션을 모두 잃으면 복구할 수 없다.
4. **계정에서 탈퇴**: 현재 개인 로그인 코드를 한 번 확인하고 삭제한다. 별도의 탈퇴 사유나 이메일 확인은 받지 않는다. 기존 메모·대화 삭제, 공유 중인 회의록의 작성자 비우기, 팀장 승계 규칙은 유지한다. 마지막 팀원이 탈퇴하면 팀 전체를 삭제한다.
5. **기존 계정 호환**: 신규 가입 API는 이메일·비밀번호를 받지 않는다. 기존 이메일 계정은 기존 비밀번호로 계속 로그인·탈퇴할 수 있다. 테스트·평가 자료를 만드는 내부 함수는 기존 계정 구조를 지원하지만 신규 가입 화면과 API에서는 사용하지 않는다.

개인 코드 변경도 새 코드를 먼저 보관한 다음 현재 코드로 본인을 확인해 적용한다. 변경 응답을 잃어도 보관한 새 코드로 다시 들어갈 수 있다. 이전 코드로 새로 로그인할 수 없지만, 이미 로그인한 기기의 세션은 각 만료 시각까지 유지된다. 코드를 화면에서 다시 조회하거나, 이름·팀 초대 코드로 잃어버린 개인 계정을 찾는 기능은 제공하지 않는다.

같은 발급권을 반복 사용해 계정이 생기지 않도록 발급권 해시와 만료 시각을 저장한다. 코드 원문·발급권 원문·사용자 ID·팀 ID는 이 이력에 넣지 않는다. 만료 뒤 다음 성공한 가입·코드 변경 때 정리한다. 계정 삭제·코드 변경 후에도 만료 전 발급권의 재사용은 거부한다. 동시 재시도는 하나만 성공하고, 실패한 가입·변경은 발급권 소모도 함께 되돌린다.

이 흐름은 이메일 수집과 직접 작성할 항목을 줄이기 위한 설계 판단이다. 코드 보관 부담이 없어졌다는 뜻은 아니며, 실제 사용자에게 더 편한지는 별도의 사용성 확인이 필요하다. 운영 적용 전에는 `008_email_free_accounts.sql`·`009_consumed_auth_tickets.sql` 마이그레이션이 필요하다.
